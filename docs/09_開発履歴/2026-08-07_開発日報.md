## 2. pets RLS 本番化

開発用 allow-all Policy を撤去し、本番 RLS を Supabase に適用した。

### 削除した開発用 Policy

- `pets_allow_all_for_development`
- `Development pets insert` / `Development pets select` / `Development pets update`

### 適用した本番 Policy

| Policy                         | 内容                      |
| ------------------------------ | ------------------------- |
| `pets_select_breeder_own`      | 本人所有 pet（全 status） |
| `pets_select_public_published` | 公開中 pet のみ           |
| `pets_select_admin`            | admin 全件 SELECT         |
| `pets_insert_breeder_own`      | 本人・draft のみ INSERT   |
| `pets_update_breeder_own`      | 本人 UPDATE               |

admin UPDATE Policy は審査機能未実装のため未追加。

Migration: `20260807120000_harden_pets_rls.sql`（適用済み）

## 3. pets status Trigger

`BEFORE UPDATE OF status` トリガーで許可遷移のみ通す設計を確定し、Supabase に適用した。

| 主体            | 許可遷移               |
| --------------- | ---------------------- |
| breeder（本人） | `draft → under_review` |

関数: `public.enforce_pets_status_transition()`  
Trigger: `pets_enforce_status_transition`

admin による status 変更は AD-10 / AD-11 実装時に一体設計（今回 Trigger には含めない）。

Migration: `20260807130000_enforce_pets_status_transition.sql`（適用済み）

## 4. status Trigger セキュリティ試験

`scripts/test-pets-status-trigger.mts` により、Server Action を経由せず authenticated JWT で直接 UPDATE し、Trigger / RLS の防御を確認した。

| 段階    | 内容                                                         | 結果                                   |
| ------- | ------------------------------------------------------------ | -------------------------------------- |
| 第1段階 | 通常 UPDATE、Trigger による不正遷移拒否                      | **7 passed / 0 failed**                |
| 第2段階 | `draft→under_review` 許可、`under_review` からの不正遷移拒否 | **13 passed / 0 failed**（第1+2 合算） |
| 第3段階 | 他ブリーダー pet の SELECT / UPDATE 分離（RLS）              | **6 passed / 0 failed**                |

実行例（第3段階）:

```bash
npx tsx scripts/test-pets-status-trigger.mts --phase3
```

### 第3段階で実証したこと

- ブリーダー A はブリーダー B 所有の draft pet を SELECT できない
- ブリーダー A はブリーダー B 所有の pet を UPDATE できない
- UPDATE 試行後も対象 pet はブリーダー A から SELECT できない
- pets RLS によるブリーダー間データ分離が機能している

## 5. 第3段階 途中失敗・原因・解決

第3段階の途中実行では **4 passed / 2 failed** となった。

```text
FAIL other breeder draft pet hidden by RLS (visible count 1)
FAIL other breeder pet still hidden after update attempt (visible count 1)
```

### 原因

テストアカウントの **権限（admin ロール）・`breeder_id` の前提** が正しくなかった。RLS の不具合ではなかった。

### 確認した内容

| #   | 内容                                                                                                  |
| --- | ----------------------------------------------------------------------------------------------------- |
| 1   | **admin 兼 breeder** は `pets_select_admin` により、他 breeder 所有の pet も SELECT できる            |
| 2   | **同一 `breeder_id`** のアカウントでは「他 breeder の pet」テストにならない（本人所有として扱われる） |

### 解決

- **非 admin** のテスト専用アカウントを使用する
- 対象 pet（ブリーダー B 所有）とは **別 `breeder_id`** を持つアカウント（ブリーダー A2）を作成
- `SEC_TEST_BREEDER_*` を A2 に差し替えて `--phase3` を再試験

### 最終結果

**6 passed / 0 failed**（第3段階 合格）

### 今後のテストルール（第3段階）

- admin ロールを持つアカウントを使用しない
- テスト対象 pet と同じ `breeder_id` のアカウントを使用しない
- 非 admin かつ別 breeder のテスト専用アカウントを使用する
- Service Role Key を使用しない

詳細: [2026-08-07_pets_status_第3段階RLSテスト_原因調査](./2026-08-07_pets_status_第3段階RLSテスト_原因調査.md)
