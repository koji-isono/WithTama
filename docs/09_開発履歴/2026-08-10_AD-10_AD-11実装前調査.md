## 13. トランザクション設計

### 承認時（1 業務操作）

- `pets.status`: `under_review → published`
- `pets.published_at`: 設定
- `pet_review_logs`: `action = approved`

### 差戻し時

- `pets.status`: `under_review → draft`
- `pet_review_logs`: `action = returned`, `comment` 必須

### 評価

| 方式                                             | 評価                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------- |
| Server Action + 複数 Supabase JS クエリ          | **非原子的**。途中失敗で status のみ変わる / ログのみ残るリスク      |
| PostgreSQL RPC（単一関数・単一トランザクション） | **推奨**。Decision No.94/105 の「専用業務操作」と整合                |
| Trigger のみ                                     | status 整合性は担保できるが **`pet_review_logs` 同時 INSERT は不可** |

**結論:** status + `published_at` + `pet_review_logs` は **同一トランザクション** が望ましい。第1期は **SECURITY INVOKER RPC** または **単一 DB 関数内で複数 DML** を推奨。Server Action は RPC 呼び出し + admin 前提再検証が適切。

`submitPetForReview` の `submitted` 接続も同様に、status UPDATE と log INSERT は **セット** で扱うべき。
