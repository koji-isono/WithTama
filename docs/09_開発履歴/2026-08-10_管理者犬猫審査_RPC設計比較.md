## 1. 結論

**方式 B（審査専用 PostgreSQL RPC / Function）を推奨する。**

具体的には:

- `approve_pet_for_publish(p_pet_id uuid)` と `return_pet_review(p_pet_id uuid, p_comment text)` の **2 関数**（または同等の 2 操作）を **SECURITY DEFINER** で実装
- **`pets_update_admin` RLS は追加しない**（admin が `pets` を直接 UPDATE できないようにする）
- **`enforce_pets_status_transition` トリガーは残し拡張**（admin も `under_review → published` / `under_review → draft` のみ許可）
- 承認・差戻しと `pet_review_logs` INSERT は **同一 DB トランザクション** で実行
- Server Action は `requireAdmin()` + RPC 呼び出し + エラーハンドリングに限定

方式 A（Server Action + `pets_update_admin` + 複数 query）は、Supabase JS クライアントが **複数 REST 呼び出しを 1 トランザクションにまとめられない** こと、および **admin への広い UPDATE 権限** により、原子性・最小権限の両面で劣る。

## 2. 方式 A の構成

```
AD-11 UI
  → approvePetForPublishAction / returnPetReviewAction  (Server Action)
      → requireAdmin()  (app_metadata.role = "admin")
      → アプリ層で breeders 条件再検証（SELECT）
      → supabase.from("pets").update({ status, published_at, ... })   // 1 回目
      → supabase.from("pet_review_logs").insert({ action, ... })      // 2 回目
```

**前提となる DB 変更:**

| 変更 | 内容 |
|------|------|
| `pets_update_admin` | admin が `pets` 行を UPDATE 可能 |
| Trigger 拡張 | admin の `under_review → published` / `draft` を許可 |

**既存 RLS との関係:**

- `pet_review_logs_insert_admin_review` は **既存**（admin + `actor_user_id = auth.uid()` + `returned`/`approved`）
- `pets` の admin UPDATE は **未実装**

## 3. 方式 A のメリット

| 項目 | 内容 |
|------|------|
| 実装の見た目 | TypeScript の Repository / Service パターンに寄せやすい（`submitPetForReview` と対称） |
| デバッグ | アプリ層ログ・型チェックが効きやすい |
| Trigger 連携 | 既存 `submitPetForReview` と同様、PostgREST UPDATE で Trigger が発火 |
| 学習コスト | チーム内で Supabase `.update()` / `.insert()` の経験が既にある |

## 4. 方式 A のリスク

| リスク | 詳細 | 深刻度 |
|--------|------|--------|
| **原子性欠如** | Supabase JS の `.update()` と `.insert()` は **別 HTTP リクエスト**。PostgREST はクライアント側の複数呼び出しを 1 トランザクションにしない | **高** |
| 途中失敗の不整合 | pets が `published` になったが `approved` ログがない／逆パターンが起こりうる | **高** |
| **過剰 UPDATE 権限** | `pets_update_admin` は **行単位** の許可。RLS は **カラム単位** を制限できない。admin が `price`・`public_display_name` 等を直接変更可能 | **高** |
| status 以外の変更 | `WITH CHECK` で「status 以外変えない」を RLS だけでは表現困難（OLD 行参照不可） | **高** |
| 業務ロジック分散 | 公開条件（No.107）が Server Action にのみ存在し、直接 API 呼び出しで bypass 可能 | **中** |
| Trigger との二重管理 | アプリが `under_review → published` を試み、Trigger も同遷移を許可する必要。条件不一致時のエラー整理が必要 | **中** |
| `published_at` 整合 | 承認時にアプリだけが `published_at` を設定。ログ INSERT 失敗時に不整合 | **高** |

**原子性の補足:** PostgreSQL トランザクションをアプリから使うには RPC か Edge Function + postgres 直結が必要。方式 A を「RPC なし」で実装すると、Decision No.97 / No.105 が求める監査証跡と矛盾しやすい。

---

## 5. 方式 B の構成

```
AD-11 UI
  → approvePetForPublishAction / returnPetReviewAction  (Server Action)
      → requireAdmin()  （二重防御・UX）
      → supabase.rpc("approve_pet_for_publish", { p_pet_id })
      → supabase.rpc("return_pet_review", { p_pet_id, p_comment })
```

**Function 内（単一トランザクション）:**

```
BEGIN  -- 暗黙（関数本体）
  1. auth.uid() IS NOT NULL 確認
  2. public.is_admin() 確認
  3. pets FOR UPDATE で行ロック + status = under_review 確認
  4. breeders JOIN で No.107 条件再検証（承認時のみ）
  5. comment 検証（差戻し時）
  6. pets UPDATE（status, published_at, updated_by, updated_at）
     → Trigger: enforce_pets_status_transition 発火
  7. pet_review_logs INSERT（actor_user_id = auth.uid()）
COMMIT
```

**推奨関数シグネチャ:**

| 関数 | 引数 | 戻り値 |
|------|------|--------|
| `approve_pet_for_publish` | `p_pet_id uuid` | `void` または結果 json |
| `return_pet_review` | `p_pet_id uuid`, `p_comment text` | 同上 |

- **`actor_user_id` 引数は持たない**（No.105: `auth.uid()` のみ）
- dynamic SQL 不使用

**既存パターン:** `set_main_pet_photo`（SECURITY DEFINER + 内部で `auth.uid()` 検証 + REVOKE/GRANT）がプロジェクト内 precedent。

## 6. 方式 B のメリット

| 項目 | 内容 |
|------|------|
| **原子性** | status 更新 + `published_at` + log INSERT が 1 トランザクション |
| **最小権限** | `pets_update_admin` 不要。状態変更は Function 経由のみ |
| **監査整合** | No.97 / No.105 の「業務操作 = 状態 + ログ」を DB で保証 |
| **公開条件の正本** | No.107 の 6 条件を Function 内に集約。Server Action は薄いラッパ |
| **Trigger との整合** | Function が UPDATE して Trigger が最終防御。RPC 迂回設計にならない |
| **テスト** | SQL / `tsx` スクリプトで admin JWT から RPC を直接検証可能 |
| Decision No.94 整合 | 汎用 status UPDATE ではなく専用業務操作 |

---

## 7. 方式 B のリスク

| リスク | 詳細 | 緩和策 |
|--------|------|--------|
| SECURITY DEFINER の複雑さ | RLS bypass。内部チェック漏れが致命的 | `is_admin()` + `auth.uid()` + 行ロック + 明示条件。`SET search_path = public` |
| ロジックが DB に寄る | Migration レビュー・テストが必要 | 既存 Trigger / `set_main_pet_photo` と同様の運用 |
| 二重 admin チェック | Server + DB で重複 | 意図的（Defense in depth）。DB が最終防衛 |
| DEFINER 所有者権限 | テーブル owner として RLS を bypass | Function 内で必要最小の DML のみ。広い UPDATE 禁止 |
| エラーメッセージ | DB EXCEPTION の UX | Server Action でユーザー向けメッセージに変換 |

---

## 8. SECURITY DEFINER / INVOKER 比較

| 観点 | SECURITY INVOKER | SECURITY DEFINER（推奨） |
|------|------------------|--------------------------|
| RLS | 呼び出し元 JWT の RLS が適用 | 関数 owner 権限で **RLS bypass** |
| `pets` UPDATE | **`pets_update_admin` が必須** | Function 内 UPDATE で可。**admin 直接 UPDATE 不要** |
| admin 確認 | RLS + Function 先頭 | Function 先頭で `is_admin()` |
| `auth.uid()` | 呼び出し元 JWT | PostgREST 経由なら **呼び出し元 JWT を保持** |
| Trigger | 発火する | 発火する（UPDATE 時） |
| 最小権限 | `pets_update_admin` 追加が必要 | **`pets_update_admin` 不要** |
| 既存 precedent | Trigger は INVOKER | `set_main_pet_photo` は DEFINER |
| SQL Injection | 引数型固定なら低リスク | 同上。dynamic SQL 禁止 |

**結論:** `pets_update_admin` を避けるなら **SECURITY DEFINER が実質必須**。INVOKER で同等を実現するには admin への広い UPDATE RLS が必要になり、方式 A の弱点を引き込む。

**DEFINER 必須の安全要件（チェックリスト）:**

| 要件 | 内容 |
|------|------|
| `SET search_path = public` | 固定 |
| `auth.uid() IS NOT NULL` | NULL 拒否 |
| `public.is_admin()` | app_metadata 正本（No.102） |
| `actor_user_id` | 引数禁止。`auth.uid()` のみ |
| `REVOKE EXECUTE FROM PUBLIC` | 必須 |
| `GRANT EXECUTE TO authenticated` | Function 内で admin 以外は拒否 |
| anon EXECUTE | 付与しない |
| dynamic SQL | 使用しない |
| 公開条件 | Function 内再検証（No.107） |

## 9. RLS との役割分担

| レイヤー | 役割 | 管理者審査での位置づけ |
|---------|------|------------------------|
| **RLS** | 行へのアクセス可否（SELECT / INSERT / UPDATE / DELETE） | admin SELECT（pets / breeders / pet_photos / logs）は既存。`pets` admin UPDATE は **付与しない** |
| **RPC (DEFINER)** | 業務操作（条件検証 + 複数 DML + トランザクション） | 承認・差戻しの **唯一の状態変更経路** |
| **Trigger** | status 遷移 allowlist | breeder / admin 各 1 パターンのみ。最終防御 |

**`pets_update_admin` は必要か:** **不要（推奨）。** admin が PostgREST 経由で `pets` を直接 UPDATE できないようにし、審査専用 RPC のみが status を変更する。

**`pet_review_logs` RLS:** 既存 `pet_review_logs_insert_admin_review` は残す。RPC（DEFINER）内 INSERT は RLS を bypass するが、Function 内で admin + action + actor を検証するため整合する。

## 10. status Trigger との役割分担

**現状（Migration 正本）:**

```sql
-- Phase 1: draft → under_review（breeder 本人のみ）
-- それ以外はすべて RAISE EXCEPTION
```

**推奨拡張（将来 Migration）:**

| 主体 | 遷移 | Trigger 条件 |
|------|------|-------------|
| breeder | `draft → under_review` | `breeders.user_id = auth.uid()`（現状維持） |
| admin | `under_review → published` | `public.is_admin()` |
| admin | `under_review → draft` | `public.is_admin()` |

**Trigger を残す理由:**

- RPC があっても **Trigger は削除・迂回しない**（設計原則）
- admin でも **任意 status 変更は不可**（`draft → published` 等は拒否）
- 将来 `pets_update_admin` を誤追加しても Trigger が二次防御
- breeder フロー（`submitPetForReview`）は現状の UPDATE + Trigger のまま維持可能

**Trigger が担わないもの（RPC 側）:**

- No.107 ブリーダー公開条件（6 条件）
- `published_at` 設定
- `pet_review_logs` INSERT
- 差戻し `comment` 必須（DB CHECK は `pet_review_logs` 側に既存）

**admin 兼 breeder アカウント:** Trigger 内で `is_admin()` 分支を先に評価するか、遷移ごとに主体を明示。第1期は admin 操作は RPC 経由のみとし、Trigger の admin 分支は `is_admin()` で十分。

## 11. pet_review_logs の原子性

**同一トランザクション必須: はい。**

防ぎたい不整合:

| 不整合 | 方式 A | 方式 B |
|--------|--------|--------|
| `published` だが `approved` ログなし | 起こりうる | 防止 |
| `draft` だが `returned` ログなし | 起こりうる | 防止 |
| ログのみ追加で status 不変 | 起こりうる | 防止 |

**補足:** `pet_review_logs` 単体の CHECK 制約（`returned` は comment 必須）は既存 Migration に存在。クロステーブル整合（status と log の対応）は **Function + 単一トランザクション** が現実的。

**breeder `submitted` も同様:** `submitPetForReview` の将来改修も status UPDATE + log INSERT を 1 トランザクション（`submit_pet_for_review` RPC 化）が望ましい。管理者審査と対称。

## 12. published_at 設計

| 操作 | status | published_at | 根拠 |
|------|--------|--------------|------|
| 承認 | `under_review → published` | `now()` を設定 | pets.md「初回公開日時」。No.107 承認フロー |
| 差戻し | `under_review → draft` | **変更しない（NULL のまま）** | 第1期は `under_review` からの差戻しのみ。未公開のため NULL が正 |

**差戻し時の DB 保証:**

| レベル | 内容 | 推奨 |
|--------|------|------|
| 前提 | 第1期に `published → draft` なし | 設計上保証 |
| Function | `return_pet_review` で `OLD.status = under_review` を確認 | **必須** |
| 防御的 | `published_at IS NULL` も確認してから差戻し | **推奨**（データ異常検知） |
| Trigger | `under_review → draft` 時に `NEW.published_at` を NULL 固定 | **任意**（第1期は RPC 側で十分） |

**承認時:**

- `published_at = now()` を RPC 内で `status` UPDATE と同時設定
- 将来「再公開」が入る場合は `published_at` 上書き禁止ルールを別 Decision で定義（第1期は初回のみ）

## 13. セキュリティ評価

| 観点 | 方式 A | 方式 B（推奨） |
|------|--------|----------------|
| admin 判定 | Server Action のみ → bypass 可能 | Server + `is_admin()` in Function |
| RLS | `pets_update_admin` で過剰権限 | admin `pets` 直接 UPDATE 不可 |
| Trigger | 拡張必要 | 拡張 + RPC と二重防御 |
| `actor_user_id` | クライアント指定リスク（RLS で防御） | 引数なし + `auth.uid()` |
| 任意 status 変更 | admin UPDATE + Trigger 拡張漏れで危険 | Trigger allowlist + RPC 限定 |
| 他 admin 以外の承認 | RLS + Trigger | Function 内 `is_admin()` |
| Service Role | 不使用（両方式） | 不使用 |
| 未承認ブリーダー公開 | Server 検証のみなら bypass | Function 内 No.107 再検証 |
| 登録期限切れ公開 | 同上 | Function 内 `registration_expires_at >= CURRENT_DATE` |
| Signed URL | 本比較の範囲外（既存 admin SELECT RLS） | 同左 |

**Decision 整合:**

| Decision | 整合 |
|----------|------|
| No.96 | 差戻し `under_review → draft` + comment — RPC + Trigger + CHECK |
| No.101 / No.107 | 公開条件 6 項目 — RPC 内再検証 |
| No.102 | `is_admin()` / app_metadata — Trigger + Function |
| No.105 | `actor_user_id = auth.uid()`、log 追記のみ — RPC INSERT |

## 最終回答

| 質問 | 回答 |
|------|------|
| **方式 A / B どちらを推奨か** | **方式 B（審査専用 RPC）** |
| **理由** | 単一トランザクションで監査整合を保証でき、`pets_update_admin` 不要で最小権限を実現。Trigger と併用して多層防御。Decision No.94 / No.97 / No.105 / No.107 と整合 |
| **`pets_update_admin` が必要か** | **不要（作成しないことを推奨）** |
| **SECURITY DEFINER が必要か** | **はい**（`pets` 直接 UPDATE RLS を付けない前提では実質必須） |
| **status Trigger を残すか** | **はい。拡張して admin 2 遷移のみ追加許可** |
| **承認/差戻しと log を同一トランザクションにするか** | **はい（必須）** |
| **次に作る Migration** | **`enforce_pets_status_transition` admin 拡張 + `approve_pet_for_publish` / `return_pet_review` RPC（SECURITY DEFINER）**。`pets_update_admin` は含めない |
