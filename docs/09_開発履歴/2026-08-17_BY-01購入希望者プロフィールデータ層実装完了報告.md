## 4. Repository

### `getBuyerProfileByUserId(userId)`

- Server Client + RLS
- `user_id = auth.uid()` 相当の行を SELECT
- BY-01 必要列のみ（13 列 + `id` / `user_id`）

### `updateBuyerProfile(userId, data)`

- `.eq("user_id", userId)` のみ（request body の buyer ID 不使用）
- 更新列は `UpdateBuyerProfileData` に限定
- `membership_status` / `user_id` / `id` は UPDATE 不可

---

## 5. Validation

- 方式: `breeder-profile/validation.ts` と同系（フィールドエラーオブジェクト + `hasValidationErrors`）
- 必須 5 項目 + 任意項目
- 都道府県: `JAPAN_PREFECTURES`（`breeder-profile/prefectures` 再利用）
- 最大長: BY-01 設計値（80 / 40 / 100 / 1000 / 100）
- 電話番号: trim + 許可文字 + 10〜11 桁（**保存正規化は行わない**、案 A 準拠）
- `parseBuyerProfileFormData`: `profile_completed` / `user_id` / `buyer_id` 等を **無視**

---

## 6. profile_completed 判定

- `isBuyerProfileComplete(normalized)` — 必須 5 項目がすべて非空
- `buildUpdateBuyerProfileData` — Server 側で `profile_completed` を算出
- クライアントから `profile_completed=true` が送られても **パース段階で無視**
- validation 失敗時は Action が UPDATE しないため `true` にならない

---

## 7. Server Action

### `saveBuyerProfileAction(formData)`

1. `supabase.auth.getUser()`
2. 未認証 → `error`
3. `isAdminUser` / `parseMemberUserRole` — buyer 以外拒否
4. FormData パース → validation
5. `getBuyerProfileByUserId(user.id)` で本人行確認
6. `updateBuyerProfile(user.id, updateData)`
7. `{ success: true, profileCompleted }` または `{ success: false, fieldErrors | error }`

**redirect なし**（UI 工程で `/buyer/dashboard` 遷移を実装）
