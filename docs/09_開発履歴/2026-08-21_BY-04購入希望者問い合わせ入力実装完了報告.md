## 認証・権限

| チェック項目               | 実装箇所                          |
| -------------------------- | --------------------------------- |
| buyer ロール必須           | `(buyer)/layout` `requireBuyer()` |
| admin / breeder 拒否       | layout + Server Action + Loader   |
| `profile_completed = true` | Loader + Server Action            |
| pet 公開状態               | Server Action（View 経由）        |
| 既存有効 inquiry           | Loader + Server Action            |

`buyer_id` / `breeder_id` / `subject` / `status` はクライアントから受け取らず、Server 側で決定。

---

## 有効 inquiry の定義（Decision No.110）

```
deleted_at IS NULL
AND status IN ('open', 'replied', 'visit_requested', 'visit_scheduled')
```

該当行が存在する場合、新規 inquiry を作成せず `/buyer/inquiries/[inquiryId]` へ誘導。

---

## subject 自動生成（Decision No.111）

購入希望者には subject 入力欄なし。Server 側で生成:

- 基本: `{public_display_name}についてのお問い合わせ`
- フォールバック: `犬猫についてのお問い合わせ`

---

## 問い合わせ作成フロー

1. 本文バリデーション（必須・空白のみ不可・最大 2000 文字）
2. buyer / profile / pet 公開状態 / 既存 inquiry を Server 側で再確認
3. `inquiries` INSERT（`status = 'open'`）
4. `inquiry_messages` INSERT（`sender_type = 'buyer'`, `sender_user_id = auth.uid()`）
5. `inquiries.last_message_at` UPDATE
6. 成功 → `/buyer/inquiries/[inquiryId]` へ redirect（クライアント `router.push`）

### トランザクション整合性

- message INSERT 失敗時 → `inquiries.deleted_at` を設定して論理削除（ロールバック）
- 競合で重複 inquiry が発生した場合 → 古い方を canonical とし、新規分を soft delete

---

## 二重送信対策

- UI: 送信中ボタン `disabled` + 「送信中...」
- Server: 送信直前の有効 inquiry 再確認

| ケース             | 方針                                       |
| ------------------ | ------------------------------------------ |

| 作成失敗           | 「送信に失敗しました。時間をおいて…」      |
