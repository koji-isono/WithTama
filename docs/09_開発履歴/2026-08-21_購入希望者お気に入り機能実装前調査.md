## 3. 現在の DB 構成

### 関係（簡略）

```
auth.users (Supabase Auth)
    │ user_id
    ▼
public.buyers ──< public.favorites >── public.pets
                                      │
                                      └── breeder_id → public.breeders
```

### `buyers`

- PK: `id`（uuid）
- 認証紐付け: `user_id` → `auth.users.id`
- RLS: 本人のみ SELECT / INSERT / UPDATE（`auth.uid() = user_id`）

### `pets`

- PK: `id`（uuid）
- ステータス: `draft` / `under_review` / `published` / …
- 論理削除: `deleted_at`

### 公開犬猫の取得方法（PU-01 / PU-02）

| 用途     | データソース                  | フィルタ条件（View 内）                                                                                                  |
| -------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 一覧     | `published_pets_public`       | `status='published'`, pet/breeder `deleted_at IS NULL`, breeder `review_status='approved'`, `membership_status='active'` |
| 詳細     | `published_pet_detail_public` | 同上                                                                                                                     |
| 判定関数 | `is_publicly_listable_pet()`  | SECURITY DEFINER                                                                                                         |

公開 Loader は **View 経由**で取得。`anon` でも閲覧可能。

### `favorites`（既存）

| カラム       | 型          | 備考                            |
| ------------ | ----------- | ------------------------------- |
| `id`         | uuid PK     |                                 |
| `buyer_id`   | uuid FK     | → `buyers.id` ON DELETE CASCADE |
| `pet_id`     | uuid FK     | → `pets.id` ON DELETE CASCADE   |
| `created_at` | timestamptz |                                 |

## 6. 推奨テーブル設計

**既存設計をそのまま採用**（変更不要）。

### `buyer_id` vs `user_id` の判断

| 方式                             | 評価                   |
| -------------------------------- | ---------------------- |
| **`buyer_id`（`buyers.id`）**    | **推奨・既存採用済み** |
| `user_id`（`auth.users.id`）直接 | 不採用                 |

**理由:**

1. `inquiries` / `visits` も `buyer_id` → `buyers.id` を使用
2. RLS は `buyers.user_id = auth.uid()` で本人判定
3. 初回ログイン時 `ensureUserProfile()` で `buyers` 行が bootstrap される（Decision No.61）
4. Server 側は `getBuyerProfileByUserId(auth.uid())` で `buyers.id` を解決し、**クライアントから `buyer_id` を受け取らない**

## 7. 推奨 RLS 設計

### 現状（migration 済み・変更不要で第1期開始可能）

| 操作   | ポリシー               | 条件                                                        |
| ------ | ---------------------- | ----------------------------------------------------------- |
| SELECT | `favorites_select_own` | `favorites.buyer_id` に紐づく `buyers.user_id = auth.uid()` |
| INSERT | `favorites_insert_own` | 同上（WITH CHECK）                                          |
| DELETE | `favorites_delete_own` | 同上                                                        |
| UPDATE | **なし**               | 設計どおり使用しない                                        |

### 第1期の追加検討（任意・次 migration）

`inquiries_insert_buyer` と同様、INSERT 時に **公開中 Pet のみ**許可する RLS 強化:

```sql
-- 参考: inquiries と同パターン（実装時 migration で追加検討）
AND EXISTS (
  SELECT 1 FROM public.pets
  WHERE pets.id = favorites.pet_id
    AND pets.deleted_at IS NULL
    AND pets.status = 'published'
)
```

| 方式                                    | メリット        | デメリット                      |
| --------------------------------------- | --------------- | ------------------------------- |
| **アプリ層のみで `published` チェック** | migration 不要  | DB 直叩き bypass の理論的可能性 |
| **RLS に `published` 条件追加**         | DB 側で二重防御 | 追加 migration が必要           |

**第1期推奨:** アプリ層で `is_publicly_listable_pet` 相当を必須チェック。余力があれば INSERT RLS 強化 migration を追加。

### セキュリティ原則

- Service Role は Server Action / Repository（`createClient()` from server）のみ
- RLS 無効化しない
- INSERT 時の `buyer_id` は **Server が `auth.getUser()` → `buyers` 行から解決**

## 12. 未ログイン時の処理案

### 現状

- `/login` は **`next` クエリ未対応**（ログイン後は常に `/buyer` or `/breeder` 入口へ）
- `sanitizeNextPath()` は `/auth/callback` にのみ存在

### 第1期推奨フロー

1. 未ログインが ♡ をクリック
2. `/login?next=/pets/{petId}` へ遷移
3. ログイン成功後、`next` があればそこへ、なければ従来どおり `/buyer` 入口
4. buyer ロール以外が `next` 付きでログインした場合 → ロール入口へ（`next` 破棄または要 Decision）

### 実現方法

- `login/page.tsx` で `useSearchParams().get("next")` を読み取り
- 成功時 `sanitizeNextPath(next)` 相当の関数を共通化
- **既存 auth 基盤で実現可能**。ただし **現時点では未実装** → お気に入り実装とセットで追加が必要

## 13. 公開停止・非公開になった犬猫の扱い

| ケース                | DB の favorites 行 | 第1期推奨 UI                                               |
| --------------------- | ------------------ | ---------------------------------------------------------- |
| `status != published` | **残る**           | **一覧に表示しない**（`published_pets_public` INNER JOIN） |
| `deleted_at` 設定     | **残る**           | **一覧に表示しない**                                       |
| `pets` 物理削除       | **CASCADE で削除** | 一覧から自然消滅                                           |

**第1期方針:** 一覧は **現在公開中の Pet のみ表示**。非公開化された Pet は一覧から消えるが、favorites 行は DB に残る（再公開時に再表示可能）。

**含めない（第1期）:** 「掲載終了」カード表示、自動 DELETE、ブリーダーへの通知。

| 5   | 同一 Pet で再クリック           | 解除、♡ に戻る                 |
| 6   | 重複登録                        | エラーなく 1 件のみ（UNIQUE）  |
| 7   | BY-02 → お気に入り              | `/buyer/favorites` へ遷移      |
| 8   | お気に入り一覧                  | 登録 Pet がカード表示          |
| 9   | 一覧カードクリック              | PU-02 詳細へ                   |
| 10  | 詳細で ♥ 表示                   | 一覧と状態一致                 |
| 11  | 他 buyer アカウント             | 他人のお気に入りが見えない     |
| 12  | 非公開化された Pet              | 一覧から非表示（行は DB 残存） |
| 13  | BY-01 プロフィール              | 非退行                         |
| 14  | PU-01 公開一覧                  | 非退行                         |

## 20. 結論

**この設計方針で実装開始してよい。**

ただし、実装着手前に以下を **必ず完了** すること。

1. **Supabase 上で `favorites` テーブル + RLS の適用確認**（未適用なら既存 migration のデプロイのみ）
2. **BY-03 画面設計書の作成**（URL `/buyer/favorites`、PU-02 追記）
3. **未決定事項の確定**（`published` 以外の登録可否 → 推奨: 不可 / `profile_completed` 要否 → 推奨: 一覧アクセスは BY-01 完了後）
4. **`/login?next=` 対応**をお気に入り実装と同時に行うこと

**新規テーブル・重複 migration は不要。** 既存 `favorites` + `buyer_id` + UNIQUE + RLS を活かし、`src/features/favorites/` と `/buyer/favorites`、PU-02 トグル、BY-02 接続の追加が最小スコープ。
