## 1. 今回トップページへ着地した直接原因

**Confirm signup が Supabase implicit flow（hash セッション）のまま動作し、最終 redirect 先が Site URL（`/`）になったため。**

メール確認自体は成功。Supabase が Site URL へ **hash 付き redirect**（`#access_token=...&type=signup`）した。

WithTama 側:

- **サーバー**は URL fragment を読めない
- **`RecoveryLinkHandler`** は hash の `type=recovery` のみ処理 → **`type=signup` は未処理**
- 結果: **トップページに留まり `/login` へ遷移しない**

---

## 2. emailRedirectTo は実際に設定されているか

**コード上は設定済み。**

```typescript
// src/lib/supabase/sign-up.ts
emailRedirectTo: getSignupEmailRedirectUrl();

// src/lib/supabase/auth-redirect.ts
return `${getAppBaseUrl()}/auth/callback?next=/login`;
```

| 項目                   | 内容                                                      |
| ---------------------- | --------------------------------------------------------- |
| 生成 path              | `/auth/callback?next=/login`                              |
| base URL               | `NEXT_PUBLIC_APP_URL`（未設定時 `http://localhost:3000`） |
| localhost ハードコード | **なし**                                                  |

ただし **`{{ .ConfirmationURL }}` テンプレートのみでは、この redirect 経路が主経路にならない**（§4 参照）。

---

## 3. 現在の Supabase Auth flow

| 項目             | WithTama の状態                                                                     |
| ---------------- | ----------------------------------------------------------------------------------- |
| Client           | `@supabase/ssr` の `createBrowserClient`（SSR / cookie セッション = **PKCE 前提**） |
| 明示設定         | `flowType` / `detectSessionInUrl` 等の **カスタム設定なし**                         |
| `/auth/callback` | **`?code=` の PKCE exchange のみ**（`exchangeCodeForSession`）                      |
| Recovery         | **token_hash → `/auth/confirm`**（Dashboard テンプレートカスタム済み）              |
| Signup           | **デフォルト `{{ .ConfirmationURL }}` のまま** → implicit hash 側                   |

Supabase 公式（Password-based Auth）: **SSR 利用時は PKCE flow。signup 確認メールは token_hash 方式テンプレートへの変更が必要。**

---

## 4. `#access_token` 方式になった理由

**Implicit flow（fragment セッション）** によるもの。

- メールリンクを **別ブラウザ / メールアプリ内ブラウザ** で開く
- PKCE code verifier が signup 元ブラウザにない
- デフォルト `ConfirmationURL` は **hash に access_token / refresh_token を返す**（Supabase Implicit flow ドキュメント）
- fragment 内 `type=signup` は implicit signup 確認の典型

---

## 5. `/auth/callback` へ来なかった理由

| 要因           | 説明                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| テンプレート   | `{{ .ConfirmationURL }}` は PKCE 用にカスタムされていない → **Site URL + hash** 着地           |
| アーキテクチャ | `/auth/callback` は **`?code=` のみ**処理。hash は server route 非対応                         |
| Redirect URL   | signup callback 登録は正しいが、**implicit + デフォルト ConfirmationURL では主経路にならない** |
| クライアント   | `RecoveryLinkHandler` が signup hash を処理しない                                              |

**ユーザー確認（ログ禁止）:** メール内 Supabase verify URL に `redirect_to=` が含まれるか目視可能。含まれていても今回テンプレート構成では **Site URL + hash** になり得る。

---

## 6. `ConfirmationURL` 維持が適切か

**WithTama（SSR + `/auth/callback` + `/auth/confirm`）では不適切。**

| 方式                                          | 評価                                                                               |
| --------------------------------------------- | ---------------------------------------------------------------------------------- |
| A: `{{ .ConfirmationURL }}` + emailRedirectTo | SSR/PKCE 向けに Supabase 公式非推奨。implicit hash になり server callback と不整合 |
| B: token_hash + `/auth/confirm`               | Recovery 同型。既存実装 + Supabase SSR 公式ガイドと一致                            |

---

## 7. token_hash + `/auth/confirm` へ変更すべきか

**はい（推奨）。**

Recovery で実証済みの方式を signup に適用:

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup&next=/login">
  メールアドレスを確認する
</a>
```

Supabase 公式例は `type=email` も使用。WithTama `/auth/confirm` は recovery 以外を `/login` へ redirect する実装済み。

**Recovery への影響: なし**（Reset password テンプレートは変更しない）。

## 8. Supabase Dashboard で必要な変更

| 項目                            | 対応                                         |

| Redirect URLs                   | Recovery 2 件 + signup callback **維持で可** |
| Site URL                        | `http://localhost:3000` 維持                 |

token_hash 直リンクは同一 origin の `/auth/confirm` へ直接のため、Redirect URL への **必須追加はない**。

Dashboard 変更は **ユーザー手動**（Cursor からは変更しない）。

## 9. コード側で追加修正が必要か

| 優先度           | 内容                                                                   |

## 10. Recovery への影響

**なし。** Confirm signup テンプレートのみ変更。Recovery の token_hash + `type=recovery` は維持。

---

## 11. セキュリティ上の推奨

| 項目                                  | 推奨                                            |
| ------------------------------------- | ----------------------------------------------- |
| hash token を標準 signup フローにする | **非推奨**（履歴・referrer 露出）               |
| token_hash + server `verifyOtp`       | **推奨**（Recovery と同じ cookie セッション化） |
| token / email / UUID のログ・報告     | **禁止**                                        |

---

## 12. 最小修正案

```
【Dashboard のみ（主）】
Confirm signup テンプレート
  → token_hash + /auth/confirm?type=signup&next=/login
  ↓
/auth/confirm → verifyOtp → /login
  ↓
通常ログイン → ensureUserProfile → role 別 entry

【コード（任意・次 commit）】
RecoveryLinkHandler: hash type=signup 着地時 /login へ（防御層）

【変更不要】
Recovery テンプレート / reset-password / Stripe Step 7
emailRedirectTo 設定は残してよい
```
